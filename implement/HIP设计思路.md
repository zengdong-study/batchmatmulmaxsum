# BatchMatmulMaxSum HIP 融合算子设计思路

本文记录当前讨论方案，不代表已经完成实现或性能验证。

## 1. 目标和约束

计算逻辑固定为：

```text
X1[B,M,K] × X2[B,K,N]
    → 对 N 取 Max
    → 对 M 求 Sum
    → y[B]，FP32
```

- 每次算子调用只能启动一次 kernel。
- 输入为 FP16 或 BF16，支持四种连续存储布局。
- 点积采用 FP32 累加或等效精度；输出与持久化 golden 比较。
- 不保存完整相似度矩阵，尽量在计算过程中完成 Max/Sum。
- 必须支持尾块、全负相似度及多次执行结果一致性。
- Max 与 Sum 不可交换；点积必须完成整个 K 的累加后才能参与 Max。

## 2. 变量定义

| 名称 | 含义 |
|---|---|
| B/M/N/K | 完整问题的矩阵维度 |
| baseM/baseN/baseK | 逻辑 tile 在 M/N/K 方向上的大小 |
| 16×16×16 | 当前讨论采用的硬件矩阵计算基本单元；具体指令及线程映射需结合目标架构确认 |
| groupBaseM | 一个 M group 覆盖的行数，是若干个 baseM 的总和 |
| groupBaseN | 一个 N group 覆盖的列数，是若干个 baseN 的总和 |
| groupB | 一个 B group 包含的 batch 数，辅助命名 |

```text
groupBaseM = M方向tile数量 × baseM
groupBaseN = N方向tile数量 × baseN
```

例如 baseM=32、baseN=64、baseK=32，groupBaseM=128、groupBaseN=128，一个二维 group 含 4×2 个逻辑输出 tile。

本文的“任务”表示独立计算范围，不直接等同于一个硬件线程。任务到 thread block、wave、线程的具体映射尚未确定；矩阵指令路径需要相应线程协作。

## 3. 按输入规模选择切分方向

### 3.1 B 提供足够并行度：沿 B 分配任务

一个任务负责一个 B 或 groupB 个 B，在任务内部遍历 M/N/K，完成该 batch 的全部 Max 和 Sum，直接写 y[b]。

```text
任务数量 = ceil(B / groupB)
```

优点是不同任务不需要合并同一个 batch 的结果。适用于 B 已能提供足够并行度且每个 batch 工作量适中的场景。

B 最大为 64，不能仅凭 B 接近上限就认定 GPU 并行度足够。M/N 很大时，一个任务负责完整 batch 也可能运行过久。即使不沿 M/N 分配独立任务，任务内部仍需 tile 化。

不同 batch 没有输入数据复用，沿 B 分组主要用于摊薄小矩阵的任务组织开销。

### 3.2 B 小、M 大：沿 M 分配任务

一个任务负责一个 batch 的 groupBaseM 行，遍历完整 N/K。

```text
任务数量 = B × ceil(M / groupBaseM)
```

每行完成 N 方向的 Max，再在任务内部沿 M 求和，每个任务只写一个部分和。同一 batch 的部分和最终合并得到 y[b]。

```text
每个M group：
    对其负责的每一行，计算完整N范围的最大值
    对这些行最大值求和
    写出一个partialSum

同B所有partialSum求和 → y[b]
```

M 方向可以直接分解为独立的最终求和项，因此作为通用主路径优先考虑。增大 groupBaseM 可以减少部分和数量，并在合适的循环组织下复用 X2。

### 3.3 B/M 小、N 大：沿 N 分配任务

一个任务负责一个 batch 的 groupBaseN 列，覆盖全部 M 行并遍历完整 K。

```text
任务数量 = B × ceil(N / groupBaseN)
```

每个任务写出 M 个局部最大值：

```text
partialMax[b, nGroup, m]
```

最终先跨 N group 对每行取 Max，再沿 M 求和。

不能先将每个 N group 的行最大值求和。例如两个 group 分别得到 [10,1]、[1,10]，正确结果是 20，两个局部和 11 无法恢复正确答案。

该路径适合 M 较小的情况。增大 groupBaseN 可以复用 X1、减少局部最大值数量及最终归约成本，但也会降低独立任务数量。

### 3.4 B/M/N 都小：比较矩阵指令与 SIMD

- K 较小：协作、加载和归约开销可能占主导，需验证 SIMD 路径是否更快。
- K 较大：考虑任务内部沿 K 分工，再协作合并点积；同时评估矩阵指令的有效利用率。
- M=N=1、N=1、M=1 等退化形状可采用专用路径。
- 分支依据形状、dtype 和布局选择，不依据 case 编号或输入内容选择。

## 4. Group 的执行方式

切分决定独立任务边界；group 决定一个任务连续处理多少个 tile。基本 tile 和任务粒度应分开调优。

### 同时处理多个 tile

多个 tile 共享当前加载的输入，可能增加数据复用，但需要更多累加器、寄存器或 LDS。

例如多个 M tile 同时使用当前 X2 tile，可以增加 X2 复用，但必须同时保留相应计算状态。

### 顺序处理多个 tile

沿用同一套计算资源，逐步合并 Max 或 Sum，资源占用更容易控制，但单个任务运行时间增加。

沿 N 分组时：

```text
遍历group内的baseN块
    完成该块的完整K点积
    更新每行的运行最大值
最后写出group的局部Max
```

沿 M 分组时：

```text
遍历group内的baseM块
    得到这些行在完整N范围内的Max
    累加到任务内部Sum
最后只写出一个部分和
```

若每个 M tile 都独立遍历完整 N/K，不能默认获得显式的跨 M tile 的 X2 复用；收益取决于循环顺序和资源组织。

| group 大小 | 主要取舍 |
|---|---|
| 较小 | 任务多、并行度高；重复加载和最终归约工作更多 |
| 较大 | 任务少、可增加复用、减少部分结果；可能并行度不足或资源占用过高 |

最终完成计数应统计 group 任务数量，而不是任务内部的 tile 数量。

## 5. 单次 kernel 内的最终汇总

沿 M/N 切分后，不能再启动第二个归约 kernel，需要在本次 kernel 内完成结果汇总。

### 直接浮点 atomicAdd

沿 M 切分时可以将部分和原子累加到 y[b]，但需要预先清零，且浮点累加顺序不固定，不能保证多次结果完全一致。因此暂不作为首选。

### 最后完成的任务负责收尾

候选方案：

1. 每个任务写入自己负责的部分结果。
2. 通过具有正确内存顺序的完成计数发布结果。
3. 同一 batch 的最后一个任务确认所有结果可见后，执行最终归约。
4. 沿 M 切分时归约部分和；沿 N 切分时先逐行 Max，再 Sum。
5. 采用固定的归约组织，避免由任务完成顺序决定浮点求和顺序。

计数器在本次调用前必须处于已知状态。临时空间申请、初始化是否允许、初始化如何满足单次 kernel 限制，以及重复调用/并发调用时的缓冲区隔离，仍需结合评测接口明确。

普通跨 block 自旋屏障不可直接使用：等待任务可能占满执行资源，使尚未运行的生产者无法执行，造成死锁。完成计数也不能替代正确的内存发布与读取协议。

## 6. K 方向切分

切 K 与切 M/N 不同。切 K 得到的是部分点积，必须按以下顺序处理：

```text
各K块的部分点积
    → 合并同一个(m,n)的点积
    → Max(N)
    → Sum(M)
```

不能对各 K块先取 Max 再合并。

优先考虑任务内部沿 K 分工。跨 block 切 K 往往需要保存更多部分点积，并引入跨任务同步，在单次 kernel 限制下复杂度更高，暂作为后续评估项。

## 7. 四种布局与数据搬运

逻辑元素的存储偏移：

| 输入 | 属性为 false | 属性为 true |
|---|---|---|
| X1[b,m,k] | b*M*K + m*K + k | b*M*K + k*M + m |
| X2[b,k,n] | b*K*N + k*N + n | b*K*N + n*K + k |

考虑用编译期模板生成四种加载路径，直接按实际存储布局读取，整理为计算所需的 LDS 布局，避免额外启动转置 kernel。

后续重点：

- 按输入连续维组织合并访存。
- 协调全局内存、LDS、寄存器之间的复用。
- 根据矩阵指令累加器的 lane 分布设计行 Max，减少额外搬运。
- 正确性稳定后评估双缓冲、加载与计算重叠。

## 8. 数值与尾块处理

- 点积完成整个 K 后才能取 Max。
- K 尾部无效元素补零。
- N 尾部无效候选使用负无穷，不能使用零。
- 行 Max 初值为负无穷，正确处理全负相似度。
- M 尾部无效行不参与 Sum。
- Sum 优先采用固定的树形归约，关注长 M 和正负抵消。
- FP64 最终求和可作为精度不足时的评估选项，但不能修复点积阶段的误差。

## 9. 待确认与验证

1. 目标 GPU 架构、矩阵指令和 wave/thread block 映射。
2. 评测接口对临时空间和初始化操作的限制，尤其是一次 kernel 下的计数器初始化。
3. baseM/baseN/baseK 与 groupBaseM/groupBaseN/groupB 的候选配置。
4. 沿 B/M/N 三条路径的选择阈值，以及是否需要混合切分。
5. 小矩阵的矩阵指令与 SIMD 性能对比。
6. 大 K 时任务内部切 K 的收益，以及是否确有必要跨 block 切 K。
7. 用现有 40 个持久化 case 检查正确性、重复执行一致性和性能。

当前倾向：沿 B 独立计算作为简单路径，沿 M 分组作为通用主路径，M 小且 N 大时沿 N 分组；小规模比较 SIMD 与矩阵指令，谨慎引入跨 block 切 K。
