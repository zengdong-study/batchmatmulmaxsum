# 全面超越拆分基线：优化思路与阶段验收计划

日期：2026-10-28。本文记录优化计划；实施状态以各阶段报告为准。

实施进度：S0已完成，见[阶段结论](results/s0_20261028/S0结论.md)与[完整报告](results/s0_20261028/S0报告.md)。S1–S6尚未由本轮任务启动。

## 1. 目标与验收边界

最终目标按现有40个持久化case定义：同一正式入口根据B/M/N/K、dtype、布局等问题元数据选择融合实现，40/40正确且逐case快于拆分基线。不是所有候选配置都要胜出，也不能用逐case离线挑最小值代替实际入口的测量。这里的全面只针对这40case，不等于证明任意形状和输入都更快。

保留原约束：

- 每次调用只启动一个kernel；不通过回退到多kernel的原生组合满足性能目标。
- 只用原40case，不生成新输入、不利用case编号/输入数值分布/golden进行分派或捷径计算。
- Small专用计时仍为原22case；Split-B既有范围不变。27/32和33–36由其他适用路径单独纳入最终入口验收，不扩大Small专项范围。
- 正式每项保持10次预热、100次device执行的算术平均；搬运、分配、捕获、golden检查在计时外。kernel内部的数据整理、LDS搬运、部分结果发布、归约及状态复位全部计时。
- 不把依赖输入的transpose/pack/预计算藏在计时外，不跨调用复用依赖旧输入内容的缓存。
- 初次workspace分配/状态初始化如需在调用外完成，必须属于已明确允许的接口契约；否则不能作为最终方案的前提。
- 与现有FP32 bmm→amax→sum拆分基线比较，冻结dtype转换、布局解释、精度和计时口径。可增加低精度原生GEMM作诊断对照，不能替换原基线以制造胜出。
- 继续使用原golden及现有混合误差检查；正式精度规则的歧义在最终交付前明确，不通过放宽误差换速度。

建议设两层性能门槛：硬门槛为40/40逐项加速比>1；工程目标为最慢case也留至少5%余量。临界结果用5轮独立完整10/100、基线/融合交错顺序确认；保存每轮均值，不能把500次合并成一项，也不取多轮最小值。要称为稳定胜出，不能有轮次落回基线之后。5%是计划建议，不是已证实收益或用户新增约束。

## 2. 从结果确定优先级

| 分组 | 当前证据 | 优先方向 |
|---|---|---|
| 1–8、25/26/28/29/31 | Small当前已超过其同轮拆分基线 | 保留已胜出实现，避免通用大tile或跨block协议拖慢 |
| 9–16：B4/M32/N1024/K128 | Small/Split-B不足；独立细粒度Split-N观察到优势 | 优先复用N group64/waves2候选，统一基线验证后集成 |
| 17–24：B1/M65/N129/K8192 | Small仍慢约1.45–7.44倍，布局差异大 | 低B任务并行度、长K GEMM主循环和协作加载，不只调wave数量 |
| 30：B2/M33/N65/K8192 | 当前约慢2.16倍，且有抵消数值特征 | 与长K路径一起处理，额外关注累加顺序/误差 |
| 27/32：N=1 | 独立Split-M有优势，尚未并入统一入口 | GEMV/点积后Sum专用路径，不强行走一般N维矩阵归约 |
| 37–40：B64/M=N8192/K128 | Split-B仍慢约1.29–2.61倍 | M/N二维block网格、宏tile复用与流式行Max，控制收尾流量 |
| 33–36：B1/M=N=K8192 | 本轮未覆盖，只有旧拆分基线 | 按冻结规格生成本地缓存、建立资源与耗时预算，再验证大GEMM路径 |

Split-N、Split-M结果来自其自己的设备/库/基线身份，不能直接与Small结果拼成“已全面胜出”。它们是下一阶段可复用候选，不应再从零实现同样的切分。

## 3. 原生实现研究要交付什么

先识别本机实际执行的GEMM与两个reduction，而不是先假设其后端、tile或指令。已有本地入口：

- PyTorch安装中的ATen/native归约与线性代数头文件；完整源码需要与安装版本/commit对应，头文件不等于全部实现。
- `/opt/rocm/lib/rocblas/library/*gfx1100*.hsaco`；根据trace实际kernel/solution定位对应code object，若实际走其他后端则跟随实际路径，不指定一个后端作为“原生”。
- rocWMMA协作加载和双LDS缓冲的性能示例，可借鉴数据流，不能把面向其他架构的MFMA参数照搬到gfx1100。

每组选一个或少数现有代表case，采集以下对照表；所有profiling与正式计时分开运行：

| 层次 | 核对项 | 要回答的问题 |
|---|---|---|
| 整条链 | 实际kernel/API数量、每个阶段device时间、临时流量 | GEMM、Max、Sum各花多少时间？融合能省下多少预算？ |
| task / block | 网格、M/N/K职责、每block任务量、可驻留block与任务波次 | 是任务数不足，还是每个任务执行低效？ |
| thread / wave | 加载lane映射、MMA wave tile、归约线程组织 | 合并加载、交换和有效MMA工作比例如何？ |
| global / cache | 向量加载宽度、每CTA读量、跨CTA重复读、布局尾块 | 带宽利用差，还是加载请求/地址/依赖过多？ |
| LDS | tile布局、padding/swizzle、bank冲突、读写字节、barrier | 用LDS换来的复用能否覆盖额外搬运与同步？ |
| VGPR / SGPR | 累加器、预取buffer、地址生命周期、spill、驻留限制 | 是指令级并行不足，还是资源过高挤掉驻留任务？ |
| 主循环 | K步长、预取深度、双buffer、独立累加器 | 下一tile加载是否真的与当前MMA重叠？ |
| 实际汇编 | WMMA/FMA、VMEM/DS、wait、barrier、分支、地址计算 | 编译器最终生成了什么？不要用源码顺序代替证据 |

优先用现有trace/元数据/反汇编，计数器只使用本机gfx1100确实支持的项目；不把静态occupancy当实测利用率，不为取指标假定硬件支持。

## 4. 实现路线

### 4.1 任务分配先于更深流水

低B场景不再限定一个batch只对应一个block。比较沿M、沿N及M/N二维划分，但要把单kernel最终归约的代价一起纳入。小块越多并不必然越快：需同时考虑GEMM复用、任务数量、部分结果和最后一个block的收尾压力。

长K的65×129输出按16×16可形成45个输出tile；这只是工作量分析，不代表45个block必定足以充分利用设备。先测试二维任务组织和更小但高效的宏tile。仍不足时再考虑block内split-K，跨block split-K放在后面。

跨block split-K必须先合并同一C[m,n]的所有K部分和，随后才能Max(N)；禁止先对K部分和各自Max再合并。它需要更多部分点积存储与同步，不能把它当成免费的并行度。

### 4.2 GEMM计算主体与融合归约分别诊断

建立诊断用GEMM主体/简化epilogue，使用相同现有输入确认tile和数据流的计算效率，再接回行Max/Sum。不将这种诊断kernel当成最终融合结果，也不跳过接回归约后的全量复测。

先比较GEMM主体与原生GEMM，再比较增加融合epilogue后的增量。若主体本身已慢于整条拆分链，优先重做主体，而不是继续优化最后几次shuffle。

### 4.3 CTA宏tile、wave tile、寄存器tile分层

CTA级协作加载A/B到LDS，多个wave分别计算输出子tile；沿N复用A、沿M复用B。保留直读/小tile路径给很小问题，不能所有形状都支付LDS和barrier成本。

第一轮只比较少量由形状与资源预算筛选的候选，例如CTA 16×64、32×64、32×128、64×64，Kstage32/64，2/4/8 waves。它们是待测起点，不是承诺采用的参数；不做全部参数笛卡尔积扫描。

资源预算先计算：每个buffer的LDS输入字节约为2×(TM×TK+TK×TN)，双buffer再乘2，另加padding和归约区；TM×TN个FP32累加器约4×TM×TN字节，按实际lane/wave映射分摊。最终以编译器分配和code object元数据为准。

### 4.4 流水和加载分层改

先单buffer正确版，再验证协作加载复用，再加双LDS buffer，最后才加更深寄存器预取。每步只改变一个主要维度。

四布局分别设计合并加载、LDS重排及寄存器组织；完整tile与尾tile分开。向量宽度必须服从实际地址对齐，不能把依赖输入的转置移到计时外。检查双buffer生产/消费barrier和所有无工作wave的参与，避免尾块死锁。

汇编必须确认“下一段加载→当前MMA→必要等待→消费下一段”，同时记录VGPR增加、spill、DS交换和同步代价；不能只以WMMA指令数或occupancy单项判断好坏。

### 4.5 融合epilogue与单kernel收尾

每个C tile完成全部K累加后立即更新行Max，避免全量相似度写回。流过N tile维护行Max，行完整后再求Sum。

沿M分块：发布每行组的部分Sum，再合并Sum。沿N分块：发布每个有效行的部分Max，先合并Max再Sum；不能对各N组的Sum做Max或直接相加。

优先复核已有最后block收尾协议并复用正确性证据。发布部分结果、计数器更新、收尾线程acquire、输出发布和计数器复位都要有明确内存顺序；不依靠全局自旋barrier或假设所有block同时驻留。工作区大小与收尾流量先建模，防止大M/N下归约反而成为瓶颈。workspace并发隔离、重复replay和失败后恢复属于接口验收的一部分。

| 阶段 | 修改和实验 | 测试、验证产物 | 通过后才能做什么 |
|---|---|---|---|
| S0 冻结口径与接口 | 建立40case覆盖矩阵、统一基线身份、GPU独占机制；确认workspace初始化契约 | 数据哈希、原生实际kernel表、各阶段时间、资源预算、尚未覆盖列表 | 才能比较来自不同模块的候选 |

| S6 冻结入口验收 | 固定分派规则与参数，不按正式计时结果现场选路 | 40case全正确、40case实际入口逐项胜出；临界项5轮交错10/100；单kernel trace；完整快照与复现命令 | 只有通过全部门槛才宣布“全面超过基线” |

## 6. 每轮执行纪律与停止条件

1. 冻结源码/库/设备/脚本/case/基线指纹并备份前版本，写明一个主要假设和预期改善的指标。
2. 编译通过后先跑现有代表case的golden、布局/尾块、覆盖写与重复一致性；失败立即保留产物并停止该候选的性能扫描。
3. 通过后做预算性单次检查，再做少量完整10/100；同时报告相对上一版和原拆分基线的比值。
4. 改动扩大后再跑受影响的现有case，不重测设备机器码完全相同且身份/协议相同的已完成项；复用必须留可审计证据。
5. profiler与正式性能分开；GPU测试按设备独占，所有入口共同执行，不能只检查Python进程名。记录实际区间及其他GPU客户端；不在未获授权时停止其他任务。
6. 结果失败或中断而未完整保存，重新执行完整10/100。已知有并行干扰的正式记录作废后独立重测，不挑干扰中恰好较快的一轮。
7. 性能增长若主要来自更大中间结果/多次初始化，必须包含真实调用成本复验；任何依赖接口放宽的方案先列为条件方案。
8. 某一case仍慢、未测或只有临界单轮胜出，就继续标为未验收；几何平均提速不能掩盖它。

每阶段至少交付：源码和库快照、case/配置清单、正确性报告、逐轮原始device时间、基线比较、GPU运行环境、汇编/资源摘要、失败与回退记录、下一阶段放行结论。
